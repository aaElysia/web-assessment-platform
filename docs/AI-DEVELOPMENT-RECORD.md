# AI 辅助开发记录（交付物 C）

> 对应 *Agentic AI Web Assessment Challenge* 的 **Deliverable C**。
> 本文**如实、具体**地记录本平台是如何借助 agentic AI 编程工具设计、构建与部署的——包括 AI 犯过的错误，以及这些错误是如何被人类发现并纠正的。它不是每一次 prompt 的流水账，而是挑出真正影响系统的关键交互与实践。

---

## 1. 工具

整个平台的设计、构建与维护都在一个 **agentic AI 编程助手**（WorkBuddy，一个与 Cursor / Claude Code / Codex 同类的 agent）协助下完成。人类操作者负责定义目标、审查每一次改动、运行验证关卡、并对最终的架构与心理测量决策负责；agent 负责读写文件、执行命令、生成代码、提出修复建议。人类始终对系统的正确性负责。

贯穿全程的一条核心原则：**绝不盲信 AI 的输出**。每一个非平凡的产物，都通过一道独立于其生成方式的机制加以校验（见 §6–§8）。

---

## 2. 问题拆解

这个开放式的挑战被拆解为以下工作流，每一条都作为一个聚焦的 agent 任务来推进：

| 工作流 | 构建内容 |
|---|---|
| 数据模型 | Prisma schema：`Participant → ResponseSession → ResponseItem`，本地 SQLite / 生产 PostgreSQL（Neon）双后端 |
| 问卷 | 60 题题库（`data/question-bank.json`）：大五人格 40 题 + AI 态度 20 题，反向表述题目已显式标记 |
| 评分引擎 | 纯函数评分器（`src/lib/scoring/score.ts`）：反向重编码、维度均值、缺失策略、Cronbach's α、Pearson 相关、探索性合成指数 |
| 结果界面 | 雷达图 + 条形图、逐维度明细、中性化解读、免责声明 |
| 管理后台 | 签名会话鉴权、聚合统计、信度/相关分析、CSV 导出、带删除与排序的提交明细 |
| 部署 | Vercel + Neon，配套 `vercel-build` 构建链与生产就绪自检门 |
| 验证 | 单元/集成测试、端到端契约测试、真实浏览器渲染冒烟、独立评分交叉验证、密钥审计 |

## 3. 给 Agent 的代表性指令

不罗列每一次 prompt，以下是对系统形态真正起作用的几条：

- *"人格用成熟框架；态度选一个你感兴趣的方向。清楚说明你测的是什么。"* → 引出大五人格 + AI 采纳态度，并以 `docs/assessment-framework.md` 作为权威规格。
- *"扮演心理测量算法审查专家，严格检查评分系统的正确性与合理性。先不要改代码，输出审查报告。"* → 一轮只读专家审查，暴露出 9 项问题（P1–P9），此后代码**仅在解释层/呈现层**修改，计算层原封不动。
- *"扮演 UX 设计师，检查 Consent / 问卷 / 结果页 / 管理后台的可用性，提出改进。"* → 第二轮只读审查（P0–P1），产出了反馈入口、隐私披露、移动端 Likert 缩写标签、结果页中性小结。
- *"在管理端加删除按钮，显示填写时间，并支持按时间排序。"* → 提交明细管理功能。
- *"把结果页的『读图提示』和下方分数列表拉开间距，避免拥挤。"* → 结果页布局修复。
- *"验证评分逻辑的正确性，并做一套可被人工在 Excel 复核的对账。"* → 催生 `scripts/verify-scoring.mjs` 的**独立重写交叉验证**（见 §5.1 案例二），而非让项目代码自我验证。

一个稳定的协作模式是：**先审查（只读），再按优先级清单实现，最后验证**。

## 4. Agent 如何参与架构设计

Agent 提出并迭代了以下架构决策：

- **Next.js 14 App Router + TypeScript**，API 路由与页面同仓，前后端一体。
- **Prisma ORM + 派生 provider**（`scripts/prisma-postgres.mjs` 在生产时把 schema 的 `provider` 改写为 `postgresql`），使同一份代码既能跑本地 SQLite，也能跑托管 Neon。
- **配置驱动的问卷**（`data/question-bank.json` + `interpretations.json`）：题目、维度、反向标记、解读文案都是数据而非硬编码，新增题目无需改评分代码。
- **自研轻量后台鉴权**（环境变量凭据 + HMAC-SHA256 签名会话 Cookie），而不是引入外部身份服务——刻意的极简。
- **把验证装置作为仓库的一等公民**（见 §6），而非事后补丁。

---

## 5. Agent 如何生成 / 修改代码

Agent 的工作是迭代式的：先生成模块，人类审查 diff，再决定接受、要求修改或否决。例子：

- 评分引擎生成后，经心理测量审查而加固（例如 CN 保留为独立反向语义维度；合成指数从"得分"降级为明确标注的*等权探索性指数*）。
- 结果页经历过两轮"审查驱动"的重写（解读措辞、免责位置、移动端 Likert 点击热区）。
- 管理后台在"人类指出测试提交会污染聚合统计"之后，新增了带级联删除的提交明细视图。

每一次改动都带描述性 commit message，并在纳入"完成"前对照测试套件审查。

## 5.1 三个真实案例：从 prompt 到纠正（含前后代码）

下面三例不是抽象总结，而是**真实发生、可在仓库里定位**的交互：某条人类指令 → Agent 生成了什么 → 人类为何、如何纠正。它们分别对应评分正确性、验证方法论、以及自动化测试的盲区。

### 案例一：合成指数的权重错误（评分正确性）

- **触发 prompt（心理测量审查）**：
  > *"你作为心理测量算法审查专家，严格检查本项目评分系统合理性与正确性。不要修改代码，先输出审查报告。"*

- **Agent 初版的问题**：它把"AI 采纳态度合成指数"写成了**两个池的平均**——先把正向四域求均值，再与反转后的 CN 求平均：

  ```text
  # 初版（早期文档记录，权重失衡）
  AI_Adoption_Index = ( mean(PU, TR, WA, LA) + (6 − mean(CN)) ) / 2
  ```

  展开后 `PU/TR/WA/LA` 各占 `1/8 = 0.125`，而 `CN` 占 `0.5`——**CN 被悄悄放大约四倍**。公式"看起来合理"，但统计上严重偏权，且会被误读为某种"加权"。

- **人类纠正（落地到代码）**：改为**五域等权**的算术平均，并锁定一条铁律——反向题只在题目级重编码一次（`6 − value`），CN 维度分**不在题目级反转、只在合成指数域级反转一次**，避免双重反转把 CN 的方向再次翻回：

  ```ts
  // src/lib/scoring/score.ts :: computeAiAdoptionIndex
  const favorable = positiveKeys.map((k) => domainScores[k] as number); // PU, TR, WA, LA
  const concern = domainScores["CN"] as number;
  const favorableConcern = likertScale + 1 - concern; // 仅此处对 CN 维度分反转一次
  return round(mean([...favorable, favorableConcern]), 4); // 5 个域等权，各 0.20
  ```

  这一改让合成指数成为诚实的"探索性等权指数"，并修正了 `docs/assessment-framework.md` 里此前写错的 `/2` 公式（同批也在其他文档更正）。

### 案例二：独立重写评分实现，杜绝"程序验证程序"

- **触发 prompt**：*"验证评分逻辑的正确性"*，并要求做一套可被人工在 Excel 中复核的对账。

- **陷阱**：若验证脚本 `import` 项目的 `score.ts` 同一套实现，对账就会退化成"用程序的结果验证程序"——系统性口径错误会全绿溜过，等于没验证。

- **人类决策（落地为 `scripts/verify-scoring.mjs`）**：**刻意不 import 任何项目代码**，用最朴素的方式重写一套评分，再与程序输出逐格对账（唯一共享的是题库配置这个"数据"，而非"实现"）：

  ```ts
  // scripts/verify-scoring.mjs —— 通道 B：独立重算（本脚本内重写，不依赖 src/lib/scoring/*）
  const favorableConcern = (likertScale + 1) - concern;        // 与项目同口径：仅域级反转 CN
  const recomputed = mean([pu, tr, wa, la, favorableConcern]); // 五域等权
  // 对账：逐格比较「程序维度分(A)」与「独立重算(B)」，容差 1e-4，并导出 CSV 供 Excel 肉眼复核
  ```

  结果：1056 个数值全部一致，且 CSV 可人在 Excel 中二次复核——把"验证"真正变成独立于生成方式的外部校验。

### 案例三：结果页"测试全绿却肉眼空白"——独立验证闭环的价值

- **背景**：结果页是**客户端渲染（CSR）**。一次改动后，单元 + E2E 测试全绿，但真实浏览器里整页只显示卡片标题，分数与图表全空。

- **Agent 的盲区**：它生成的 E2E 用 HTTP 直接取 JSON、单元测纯函数，**都不执行客户端 JS**；于是"空壳页"毫无阻碍地通过了所有自动测试。

- **人类纠正**：新增**真实浏览器渲染冒烟**（`scripts/smoke-render.mjs`，headless Chrome/Edge 实际跑客户端 JS），断言页面真的渲染出了维度名、格式化分数、分带标签、SVG 图表与合成指数；并加了一道渲染级守卫，使"空壳"无法再被当作成功。

  - **教训**：自动化测试自身也存在覆盖率盲区，必须由一道**独立于生成方式**的机制补足。这正是本文 §6、§8 反复强调的主线——也是"有效使用 AI"与"对正确性负责"的分水岭。

## 6. 如何测试 AI 生成的代码

我们把验证看得和构建一样重要。仓库自带：

- **单元与集成测试（Vitest）—— 256 项**。覆盖评分数学、反向重编码、缺失策略、维度均值、α、相关、后台守卫覆盖等。
- **端到端契约测试（`scripts/e2e-results.mjs`）**。它会创建一个真实匿名参与者、提交全部 60 题作答，并将返回的分数与**手算期望值**比对——把评分契约锁死、防止回归。
- **真实浏览器渲染冒烟（`scripts/smoke-render.mjs`）**。在 headless Chrome/Edge 中运行客户端 JS，断言结果页确实渲染出了维度名、格式化分数、分带标签、图表 SVG 与合成指数。*为何存在*：结果页是客户端渲染的；`curl` 与 E2E 套件只能看到 Suspense 空壳。曾出现一个缺陷——题库缺少 `scale.type`，导致前端找不到量表，页面只显示卡片标题——它通过了所有单元与 E2E 测试，却肉眼可见地崩了。浏览器冒烟把它抓了出来。
- **独立评分交叉验证（`scripts/verify-scoring.mjs`）**。这个脚本**不导入任何项目代码**，而是从零重写一套评分实现，再用两道独立通道对账：独立重算的逐题原始作答 vs. 程序输出的维度分，并抽样比对 `/api/results/:pid`。输出 CSV（`verify-output/crosscheck-*.csv`）供人在 Excel 中复核。*为何重写*：若两侧共用一套实现，"验证"就会退化成"程序验证自己"，系统性错误会悄悄溜过。
- **密钥审计（`audit:secrets`）与生产环境自检（`check:prod-env`）**，合并进 `deploy:check` 门（密钥扫描 + 生产自检 + 类型检查 + 测试）。
- **两轮专家审查**（心理测量、UX）在改任何代码前，作为**只读审计**执行。

## 7. AI Agent 犯过的错误

如实记录失败，本身就是交付物的一部分。具体案例：

1. **环境变量写入的 shell 语法错误。** Agent 最初在 Windows `cmd` 下建议 `DATABASE_URL="..." command`，而该写法在 `cmd` 无效。→ 改用 PowerShell `$env:DATABASE_URL='...'`。
2. **假设本机有 Node 工具链。** 一条 `npm` 建议在 Git Bash 下报 `npm: command not found`，因为机器没装 Node。→ 人类提供 Neon 连接串，Agent 直接代为执行数据库建表。
3. **`vercel-build` 因 `readlink` 报 `EISDIR` 失败。** 在某些卷（如 G: 盘）上 Node 的 `fs.readlink` 会对普通文件误报 `EISDIR`，导致 webpack 构建崩溃。→ 新增 `readlink-polyfill.cjs`，仅在 `win32` 注入。
4. **缺失 import 导致生产构建失败。** 一次结果页编辑引用了 `Button` 却没导入 → `vercel-build` 失败。→ 补上 import；`deploy:check` 门现在能拦住这类回归。
5. **单元测试对相同值误判。** `detectResponseQuality` 的测试在"两个相同值"时错误地通过。→ 测试改为使用相异值；逻辑经核实正确。
6. **一次评分改动引入了类型回归。** 给 `ResultPayload` 增加必填字段 `qualityFlags` 后，`view-model.test.ts` 的 fixture 未补齐，导致 `tsc --noEmit` 失败，本会阻断 `deploy:check`。→ 补全 fixture；这正是类型检查门存在要抓的那类回归。
7. **矛盾的知情同意措辞。** 早期 Consent 页写"你无法删除单条记录"，后来与管理端删除功能冲突。→ 改为准确表述：管理员可删除任意提交，参与者可通过反馈渠道申请删除。

以上错误没有任何一个在未被发现的情况下进入生产，都因上面的验证关卡而拦截。

## 8. 这些错误是如何被发现与纠正的

- **类型检查（`tsc --noEmit`）** 在构建前抓出缺失 import 与类型回归（第 4、6 项）。
- **`deploy:check` 门** 串联 密钥扫描 → 生产自检 → 类型检查 → 测试，使损坏状态无法被部署。
- **真实浏览器渲染冒烟**（§6）抓出了单元 + E2E 都漏掉的一次静默客户端渲染失败。
- **独立重写实现**（`verify:scoring`）为评分数学提供外部校验。
- **静态守卫覆盖扫描** 确保每一个新的 `/api/admin/*` 路由都受保护。
- **两轮只读专家审查**（心理测量 + UX）在改代码前充当由人类主导的验证。

一条主线：人类不是因为输出"看起来对"就接受它。每一个产物，都通过一道独立于其生成方式的机制进行了校验。

---

## 9. 反思

挑战赛明确写道：*仅仅接受 AI 输出是不够的*。本项目是认真践行这一点的：验证装置（独立交叉验证、浏览器冒烟、E2E 契约测试、密钥审计）本身是刻意的工程投入，而非样板代码。Agent 极大地加速了工作，但系统最终的正确性，建立在上面那条"由人类拥有的验证闭环"之上——也建立在如实记录 Agent 哪里出过错的诚实之上。
